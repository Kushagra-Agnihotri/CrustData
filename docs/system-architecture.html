01System context

Invoices land in an inbox; a crash-safe state machine verifies them against internal records and live Crustdata + IFSC data, decides PAY / HOLD / BLOCK, plans a cash-aware payment run, and pays exactly once after human approval. The UI holds no business logic — the same core is driven by the UI, worker, test runner and crash demo.

Stack

  • Python 3 + httpx
  • Streamlit, routed via st.session_state
  • SQLite WAL (Postgres-shaped schema)
  • Money = integer paise, Decimal ROUND_HALF_UP

Live data

  • Crustdata REST api-version 2025-11-01
  • Razorpay IFSC API (free)
  • Gemini 2.5 Flash only for extraction / intent fallback

Drivers

  • ui/Home.py router
  • python -m app.worker
  • scripts/run_test_set.py (21 golden cases)
  • scripts/crash_demo.py

04Data model

All money columns are INTEGER paise; timestamps ISO-8601 UTC. Every connection: journal_mode=WAL, foreign_keys=ON, busy_timeout=30000; every transition goes through db.tx() (BEGIN IMMEDIATE … COMMIT/ROLLBACK). init_schema() runs CREATE IF NOT EXISTS then column-add MIGRATIONS.

06Prompt → RunRequest (intent)

The prompt chooses which documents to evaluate. It can never switch a check off. RunRequest = {action, date_from, date_to, scope_label, vendors[], acknowledged[], refused[], source}. Out-of-scope files stay un-ingested so a later run still picks them up. “past week” = rolling 7 days; “last week” = previous Mon–Sun; bare “may” is a month only in phrases like “May invoices”. Tested in tests/test_intent.py.

07Invoice state machine

Any stage that raises unexpectedly is retried; the 3rd failure sends the invoice to HELD with PIPELINE_ERROR. A re-plan can return SCHEDULED → ELIGIBLE.

08Pipeline execution model

One transaction per transition — state, reasons, facts and the events row commit together or not at all. Each reason carries a stage tag, so re-running a stage replaces only its own reasons (idempotent). iter_pipeline is a generator yielding invoice_start · stage · invoice_done · run_done; run_pipeline just drains it.

09Duplicates & the decision engine

Level 3 is the database guaranteeing it — even a bug in levels 1–2 or a concurrent run cannot make the same identity payable twice. make_eligible also increments po_lines.qty_invoiced (CHECK refuses over-consumption) and sets PO PARTIALLY_INVOICED / CLOSED. MSME deadline: micro/small non-traders → accepted + 45 days (agreement) or + 15 days (Sec 15 MSMED / 43B(h)).

10Document extraction & validators

Parser handles pipe tables, N. item — qty x ₹price @ GST% = amount and - item x qty @ price (GST%) = amount, plus label variants, dd/mm/yyyy, “12 Nov 2026”, ISO, CGST/SGST/IGST and bank details. money.to_paise("Rs. 1,20,000/-") → 12000000. Results cached by sha256; LLM tokens and ₹ cost logged to calls. The LLM only ever returns fields.

11External sources layer

Every Crustdata / IFSC call returns Result{data, raw_response_id, retrieved_at, source_ref, mode, cached, credits, recorded} or raises SourceUnavailable. Silence is never “no problem” — it becomes a SOURCE_UNAVAILABLE hold. Faults run before the cache so cached data can’t mask an outage (case 12). 404 is an answer (cached as None). Person-search recordings keep only {count, matches:[{title, current_company_id}]}.

12Trust & priority scoring

13Cash position & payment planning

plan() is pure; propose_run() persists. Overdue receivables are never counted as cash. Tier: MSME deadline in horizon → 0; critical + overdue → 0; inside discount window with annualised (d/(1−d)) × 365/(credit − discount days) > 12 % → 1 (2/10 net 30 ≈ 37 %); else 2.

Greedy, explainable allocation

min_instalment = min(outstanding, max(25 % of total, ₹10,000)), max 3 instalments. Each proposal carries a justification JSON: tier, “₹X of ₹Y now”, reasons, cash left, and when/why the remainder is planned (“after ₹N expected from <customer> on <date>”). Alerts flag MSME deadlines ≤ 3 days and open discount windows. LP optimisation rejected: every rupee must be explainable in one sentence.

14Exactly-once payment execution

PaymentProvider protocol: create_payout(idem_key, amount_paise, beneficiary, narration) + get_status(idem_key). MockProvider keeps its own table keyed by idem_key (true idempotency, optional latency/failures). RazorpayXProvider posts /v1/payouts with X-Payout-Idempotency and refuses rzp_live_ keys. Each idem_key is a UUID created at insert and never regenerated.

Crash-safe sequence

Why no rupee is paid twice

  • 1. Intent durably written before the call
  • 2. Restart reconciles by asking about the same key first
  • 3. Provider dedupes on the key
  • 4. _mark_paid idempotent + instalments_cap trigger
  • 5. Beneficiary always the current master account, active vendors only

15Bank-change fraud defence

An email can never update the vendor master; it can only create a pending_verification account. Two entry points — an inbox email (pipeline) and paste-and-verify in the 🏦 tab (bank_verify) — converge on one maker-checker checklist. 16Evidence ledger, human actions, worker & import

Every value a decision relies on is a fact with source, exact JSON field path and retrieval time; every transition is an append-only event with an actor; every call is costed. The worker can be killed anywhere and restarted — transitions are transactional and work is claimed with expiring locks.

Safety invariants

  • Rules decide, never the LLM
  • A prompt can’t weaken a check
  • Pay only the account on file
  • An email can’t change the master
  • Silence is not OK

Money invariants

  • Each invoice paid once (3 layers, last a PK)
  • Each instalment paid once (intent-first, frozen keys)
  • Never overpay (trigger + CHECK)
  • Integer paise only
  • Every decision explainable

Production swaps

  • SQLite → Postgres/Supabase (db.py)
  • CSV/Tally → TallyPrime XML (AccountingSource)
  • Inbox → Gmail/IMAP (ingest)
  • txt/eml → PDF/OCR (extract)
  • Mock → RazorpayX live; penny mock → Account Validation; replay → live Crustdata + Watch
