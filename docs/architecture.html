The language model only extracts and explains. Deterministic rules decide.

“Match each one to its purchase order, check the vendor and its bank account, pay each one once, according to the cash we have, and hold anything unusual for my approval with the reason.”

Crash safety

Two state machines

Every transition is one database transaction: update the state, append an events row, insert any facts. The worker claims work with SELECT … FOR UPDATE SKIP LOCKED and a 60-second lease, so a killed process just lets the lease expire.

Invoice lifecycle

Instalment lifecycle: exactly once

Idempotency key = sha256(invoice_id | instalment_no | amount_paise). It is generated once and reused on every retry. A new key is never minted for the same instalment.

Worker log

Source failures are never read as answers

1Call fails or times out → retry with exponential backoff, up to 2 times.retry
2Still failing → invoice moves to HELD with SOURCE_UNAVAILABLE, naming the source.HOLD
3Crustdata 402 credits exhausted → no retry. Run stops, remaining invoices held.HOLD
4Run ceiling (time limit 900 s or 200 credits) checked before every external call → RUN_CEILING_REACHED.HOLD

Guards in the database itself

Constraints that hold even if the code is wrong

invoices UNIQUE(file_sha256)The same file dropped twice becomes the same row.
invoices UNIQUE(vendor_id, invoice_no_norm)The database refuses a second invoice with the same identity. INV/42 and INV-0042 both normalise to INV42.
instalments UNIQUE(idem_key)One provider payout per key. Retries reuse the key.
instalments UNIQUE(invoice_id, instalment_no)Instalment numbers cannot repeat. Maximum 3 per invoice.
Σ instalments ≤ invoices.totalEnforced in the same transaction. outstanding never goes below zero.
approved_by ≠ proposed_byMaker-checker on bank account changes. An email can never update the vendor master.
po_lines CHECK(qty_invoiced ≤ qty_ordered)Hard stop against re-billing an exhausted PO.
events, facts: append-onlyUPDATE and DELETE revoked for the app role. The audit trail can be replayed line by line.

How an invoice is classified

The decision is a fixed ladder. Checks attach reason codes as they run; the decider reads the codes, never the free text. The same case worded differently gets the same answer.

1Any BLOCK-level reason present?BLOCK
2Any HOLD-level reason present?HOLD
3Trust score below 0.40? → LOW_TRUST with the breakdownHOLD
4Otherwise eligible for the payment run, where tiers decide order and amount.ELIGIBLE

Reason codes

Two separate scores

Trust is a gate. Priority is an order.

A large, old company is very trustworthy but does not need paying first. A young micro supplier may be less established but is legally and economically more urgent. Missing signals score zero and are listed as “can't verify”, never imputed.

Liquidity-aware payment run

Don't clear every invoice at once. Pay by tier, in instalments where cash is short, and justify every rupee. This is a sketch of the greedy allocator running on example invoices; move the cash sliders and watch the plan re-flow.

Proposed instalments

Example data, not seed values. Tier 2 shares are proportional to priority × outstanding, with a minimum instalment of max(25% of total, ₹10,000), whole rupees, never above outstanding, at most 3 instalments per invoice. Greedy rather than LP so each line can be explained in one sentence to the approver.

Tier rules

TIER 0Must pay in full now. MSME micro/small, non-trader, deadline (accepted + 15 or 45 days) within the 7-day horizon; or a critical supplier that is overdue. If cash can't cover Tier 0, the run stops and alerts. Legal dues are never silently part-paid.
TIER 1Worth paying early. Unexpired discount whose annualised return beats the cost of cash.
TIER 2Everything else eligible and due within the horizon, ordered by priority score then due date.
